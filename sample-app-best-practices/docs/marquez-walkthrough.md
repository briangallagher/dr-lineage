# Marquez walkthrough: reading lineage and turning it into customer value

This guide explains how to inspect the lineage generated by the sample application,
what the Marquez graph means, and which customer/business questions require API
queries rather than visual inspection.

The key idea is:

    Marquez shows operational lineage.
    RHOAI must turn that lineage into customer-facing answers.

A graph is useful, but the graph alone is not the product. Users ultimately want
answers such as "where did this vector dataset come from?", "what will be affected?",
"who owns the source?", and "why did this run fail?"

## 1. Start the local services

From the application directory:

    cd /Users/briangallagher/dev/workspaces/dr-lineage/sample-app-best-practices
    ./scripts/port-forward.sh

The relevant addresses are:

| Service | Address |
| --- | --- |
| Marquez UI | http://127.0.0.1:3000 |
| Marquez API | http://127.0.0.1:5000 |
| Registry API | http://127.0.0.1:8081 |

The application containers use the in-cluster address http://marquez:80. The local
port 5000 is only a port-forward for inspection.

Set these variables for the examples below:

    export MARQUEZ=http://127.0.0.1:5000
    export REGISTRY=http://127.0.0.1:8081
    export CLUSTER=api.bgal-pool-ljt7l.aws.rh-ods.com
    export PROJECT=ol-best-practices
    export REGISTRY_NS=dataregistry://$CLUSTER/$PROJECT

The cluster value must match the cluster name used by the deployment.

## 2. What Marquez contains

The sample sends three OpenLineage event types:

| Event | Meaning | Main inspection path |
| --- | --- | --- |
| DatasetEvent | A logical dataset exists and has metadata or aliases. | Dataset entity API and dataset page. |
| RunEvent | One execution/retry attempt, with inputs, outputs, state, and facets. | /api/v1/events/lineage and job/run views. |
| JobEvent | Optional static description of a reusable job. | Job metadata; normal scenarios do not require it. |

Python code sends registry, ingestion, embedding, and root lifecycle events. The
native Spark OpenLineage listener sends Spark application and SQL events.

Marquez materializes dataset and job nodes from these events. A RunEvent connects a
job execution to input and output datasets. A DatasetEvent enriches a dataset node,
but does not claim that processing occurred.

## 3. Is there a pipeline graph?

Yes, but it is important to understand which graph it is.

Open a dataset lineage page such as:

    http://127.0.0.1:3000/lineage/dataset/<encoded namespace>/<encoded name>

Marquez shows a dataset/job lineage graph. It is not a KFP canvas containing only the
five logical pipeline boxes. It may include technical Spark application and
SQL-execution nodes because the native Spark listener reports those details.

The meaningful data path for this sample is:

    registered asset
        == symlink ==
    s3://sample-data/raw/documents.csv
        -> read-and-stage
    s3://sample-data/staging/<asset>/<ingest-run>/documents.csv
        -> native Spark application / SQL execution
    s3://sample-data/transformed/<asset>/<spark-run>
        -> create-mock-embeddings
    s3://sample-data/embeddings/<asset>/<embedding-run>/vectors.jsonl

The graph helps answer:

- Which jobs reported consuming a dataset?
- Which datasets did those jobs report producing?
- Which jobs produced a dataset?
- Which physical S3 identity is connected to the registered asset?

It does not automatically answer:

- whether source bytes were unchanged;
- whether an uninstrumented writer changed the source;
- which friendly registry name should be displayed;
- who owns the source unless ownership is joined;
- whether a failed Spark event reflects final SparkApplication state; or
- whether a result is reproducible.

Those require event facets, the registry API, Kubernetes status, or a product-level
query.

## 4. UI walkthrough

### Step 1: begin with the registered asset

The dataset URL in the question has this form:

    /lineage/dataset/<registry namespace>/<asset UUID>

The UUID-looking segment is the registry asset ID. In the current design:

    namespace = dataregistry://<cluster>/<project>
    name      = <asset UUID>

Follow the lineage relationship to the physical dataset:

    namespace = s3://sample-data
    name      = raw/documents.csv

The dataset page may expose documentation, ownership, lifecycle, and symlink facets.
The API is the reliable way to inspect the complete JSON.

### Step 2: follow the physical source downstream

The first meaningful consumer is:

    dch-mock://<cluster>/<project> / read-and-stage

Its output is a run-specific staging object. Continue downstream to Spark, transformed
Parquet, and embeddings.

Do not treat every Spark node as a separate business step. The native listener may
represent an application and one or more SQL executions. These are technical nodes
inside the single transformation stage.

### Step 3: inspect a derived dataset upstream

For a vectors JSONL dataset, follow upstream to:

1. the embedding run;
2. transformed Parquet;
3. the Spark run;
4. staged CSV;
5. the ingestion run;
6. the raw S3 object; and
7. the registry UUID symlink.

This is the "where did this come from?" experience the product should make easy.

### Step 4: inspect run details

Inspect:

- run state and timestamps;
- run ID;
- job namespace and name;
- parent/root run relationship;
- execution parameters;
- processing engine;
- input/output datasets;
- output statistics;
- schema and column lineage; and
- errorMessage facets for Python failures.

For failures, treat the KFP root status and SparkApplication status as authoritative.
The pinned Spark/OpenLineage integration can emit FAIL followed by COMPLETE for the
same native SQL run. The graph is useful, but application status and driver logs
resolve the final outcome.

## 5. API orientation

### Download RunEvents

Marquez 0.50 exposes persisted RunEvents through:

    GET /api/v1/events/lineage

Download a working copy:

    curl --silent --fail \
      "$MARQUEZ/api/v1/events/lineage?limit=10000&sort=asc" \
      > /tmp/marquez-lineage.json

Inspect a compact list:

    jq -r '.events[] |
      [.eventTime, .eventType, .run.runId, .job.namespace, .job.name] |
      @tsv' /tmp/marquez-lineage.json

This endpoint returns RunEvents. It is not the best place to retrieve the original
DatasetEvent payload or a standalone JobEvent.

In the live Marquez 0.50 deployment, the response was newest-first even when the
request included `sort=asc`. Sort the events explicitly by `eventTime` in a consumer;
do not assume the returned array is chronological.

### Read a materialized dataset entity

Marquez materializes dataset entities at:

    GET /api/v1/namespaces/{encoded namespace}/datasets/{encoded name}

For the registry asset:

    NS_ENCODED=$(jq -rn --arg v "$REGISTRY_NS" '$v|@uri')
    ASSET_ID=$(curl --silent --fail "$REGISTRY/v1/assets" | jq -r '.[0].assetId')
    NAME_ENCODED=$(jq -rn --arg v "$ASSET_ID" '$v|@uri')

    curl --silent --fail \
      "$MARQUEZ/api/v1/namespaces/$NS_ENCODED/datasets/$NAME_ENCODED" \
      | jq '{namespace, name, facets}'

Inspect the registry symlink:

    curl --silent --fail \
      "$MARQUEZ/api/v1/namespaces/$NS_ENCODED/datasets/$NAME_ENCODED" \
      | jq '.facets.symlinks.identifiers'

The entity response is where to inspect DatasetEvent documentation, ownership,
lifecycle, and symlinks.

### Find namespaces

    curl --silent --fail "$MARQUEZ/api/v1/namespaces" | jq

This helps distinguish registry, storage, and execution namespaces.

## 6. Read the event JSON correctly

| JSON path | Interpretation |
| --- | --- |
| .eventType | START, COMPLETE, FAIL, or ABORT. |
| .eventTime | Time at which the event was emitted. |
| .run.runId | One execution or retry attempt. |
| .run.facets.parent | Parent execution, normally the KFP root for child runs. |
| .run.facets.root | Root execution when supplied. |
| .run.facets.executionParameters | Asset ID, algorithm, dimensions, and similar parameters. |
| .run.facets.processing_engine | Runtime and OpenLineage adapter details. |
| .run.facets.errorMessage | Application-reported failure detail, when available. |
| .job.namespace and .job.name | Stable job identity. |
| .inputs[] | Datasets reported as consumed. |
| .outputs[] | Datasets reported as produced. |
| dataset.facets.schema | Dataset schema. |
| dataset.facets.outputStatistics | Row count, size, and file count. |
| dataset.facets.columnLineage | Field-level derivation metadata. |

A dataset is identified by the complete pair:

    (namespace, name)

Facets do not change identity. s3://bucket and s3a://bucket are different namespaces,
and a changed prefix or trailing slash can split the graph.

A run ID identifies an attempt, not a reusable job. A stable job can have many run IDs.

## 7. Queries for business value

The examples below use /tmp/marquez-lineage.json and answer questions about reported
execution history.

### Where did this vector dataset come from?

Set the target:

    export TARGET_NS=s3://sample-data
    export TARGET_NAME=embeddings/<asset-id>/<embedding-run-id>/vectors.jsonl

Find the producing run:

    jq --arg ns "$TARGET_NS" --arg name "$TARGET_NAME" '
      .events[]
      | select(any(.outputs[]?; .namespace == $ns and .name == $name))
      | {
          eventTime, eventType, runId: .run.runId, job,
          parameters: .run.facets.executionParameters,
          inputs, outputs
        }' /tmp/marquez-lineage.json

Take the input from that result and repeat until reaching the raw source. The expected
chain is embedding -> transformed -> staged -> raw.

Join the result to the customer-facing registry record:

    curl --silent --fail "$REGISTRY/v1/assets/$ASSET_ID" \
      | jq '{assetId, name, owner, description, location, lineageStatus}'

### Where is this registered asset used?

First search for direct consumers of the logical registry identity:

    jq --arg ns "$REGISTRY_NS" --arg name "$ASSET_ID" '
      .events[]
      | select(any(.inputs[]?; .namespace == $ns and .name == $name))
      | {eventTime, eventType, consumerJob: .job,
         runId: .run.runId, inputs, outputs}' \
      /tmp/marquez-lineage.json

This sample normally consumes the physical S3 identity after ingestion, so also search
for consumers of the symlink target:

    export RAW_NS=s3://sample-data
    export RAW_NAME=raw/documents.csv

    jq --arg ns "$RAW_NS" --arg name "$RAW_NAME" '
      .events[]
      | select(any(.inputs[]?; .namespace == $ns and .name == $name))
      | {eventTime, consumerJob: .job, runId: .run.runId, outputs}' \
      /tmp/marquez-lineage.json

A product asset-usage view should resolve the registry alias automatically. Users should
not need to understand that the logical and physical identities are different nodes.

### What could be affected by a source change?

Find direct downstream consumers:

    jq --arg ns "$RAW_NS" --arg name "$RAW_NAME" '
      .events[]
      | select(any(.inputs[]?; .namespace == $ns and .name == $name))
      | {
          consumer: (.job.namespace + " / " + .job.name),
          runId: .run.runId,
          producedDatasets: [.outputs[]? | .namespace + " / " + .name]
        }' /tmp/marquez-lineage.json

Repeat for staging, transformed, and embedding outputs to follow the full path. The
UI graph is convenient for exploration; a product API should compute transitive
downstream closure and show affected assets, jobs, and owners.

The current Marquez graph is not a registry-aware impact report. A product layer must
resolve symlinks, traverse edges, collapse technical Spark nodes, and join registry
ownership and display metadata. It should label the result Linked.

### Why does a derived artifact look wrong?

Find producing runs with parameters, schema, statistics, and errors:

    jq --arg ns "$TARGET_NS" --arg name "$TARGET_NAME" '
      .events[]
      | select(any(.outputs[]?; .namespace == $ns and .name == $name))
      | {
          eventTime,
          state: .eventType,
          run: .run.runId,
          job: .job,
          executionParameters: .run.facets.executionParameters,
          processingEngine: .run.facets.processing_engine,
          error: .run.facets.errorMessage,
          output: [
            .outputs[]?
            | select(.namespace == $ns and .name == $name)
            | {namespace, name, schema: .facets.schema,
               statistics: .outputFacets.outputStatistics,
               columnLineage: .facets.columnLineage}
          ]
        }' /tmp/marquez-lineage.json

Compare all producers of the same target:

    jq --arg ns "$TARGET_NS" --arg name "$TARGET_NAME" '
      .events[]
      | select(any(.outputs[]?; .namespace == $ns and .name == $name))
      | [.eventTime, .eventType, .run.runId, .job.name,
         (.run.facets.executionParameters.parameters // [] | tostring)]
      | @tsv' /tmp/marquez-lineage.json

### Who is responsible for the input?

The registry is authoritative for customer-facing ownership:

    curl --silent --fail "$REGISTRY/v1/assets/$ASSET_ID" \
      | jq '{assetId, name, owner, description, location, lineageStatus}'

The logical dataset entity also carries the emitted ownership facet:

    curl --silent --fail \
      "$MARQUEZ/api/v1/namespaces/$NS_ENCODED/datasets/$NAME_ENCODED" \
      | jq '.facets.ownership'

The values should agree. If they differ, treat the registry API as current business
metadata and the Marquez facet as the snapshot emitted with the lineage event.

Marquez cannot infer accountability from a job namespace. Ownership needs an explicit
registry join or ownership facet.

### How do RHOAI components interact?

Group events by stable job identity:

    jq -r '.events[] | [.job.namespace, .job.name] | @tsv' \
      /tmp/marquez-lineage.json | sort -u

Inspect execution hierarchy:

    jq '.events[]
      | select(.run.facets.parent != null)
      | {childRun: .run.runId, childJob: .job,
         parentJob: .run.facets.parent.job,
         parentRun: .run.facets.parent.run.runId}' \
      /tmp/marquez-lineage.json

Inspect data handoffs:

    jq '.events[]
      | select((.inputs | length) > 0 or (.outputs | length) > 0)
      | {eventTime, state: .eventType,
         job: (.job.namespace + " / " + .job.name),
         inputs: [.inputs[]? | .namespace + " / " + .name],
         outputs: [.outputs[]? | .namespace + " / " + .name]}' \
      /tmp/marquez-lineage.json

The parent facet explains execution hierarchy; matching dataset identities explain data
flow. Neither one replaces the other.

### Which runs failed?

    jq '.events[]
      | select(.eventType == "FAIL" or .eventType == "ABORT")
      | {eventTime, state: .eventType, runId: .run.runId,
         job: .job, error: .run.facets.errorMessage,
         parent: .run.facets.parent}' \
      /tmp/marquez-lineage.json

A failed child attempt does not necessarily mean the whole root run failed if KFP retried
it successfully. Use the root run and SparkApplication status for the final result.

### Which parameters and algorithm were used?

    jq '.events[]
      | select(.run.facets.executionParameters != null)
      | {runId: .run.runId, job: .job,
         parameters: .run.facets.executionParameters.parameters}' \
      /tmp/marquez-lineage.json

Embedding events include assetId, algorithm sha256-demo, dimensions 8, and mock true.
These facets describe reported execution configuration; they do not prove the source
bytes.

### What schema and column lineage were reported?

    jq '.events[]
      | .outputs[]?
      | select(.facets.schema != null or .facets.columnLineage != null)
      | {dataset: (.namespace + " / " + .name),
         schema: .facets.schema,
         columnLineage: .facets.columnLineage,
         statistics: .outputFacets.outputStatistics}' \
      /tmp/marquez-lineage.json

The embedding output reports title copied from title and embedding derived from
normalized_text. Column lineage is a declared relationship, not independent proof that
the transformation was correct.

## 8. Interpreting the UUID dataset name

The dataset name in the Marquez URL:

    01a08ba1-af04-7394-b90a-cc1557dc8b30

is the registry asset ID. In the current design:

    namespace = dataregistry://api.../ol-best-practices
    name      = registry asset UUID

This is deliberate. The UUID is a stable business anchor even if the human-readable
asset name, description, owner, or physical location changes.

### Should the dataset name be the asset name?

Usually, no. The OpenLineage dataset name is identity, not display text.

Using Customer documents as the identity would create problems:

- names can collide within a namespace;
- names can be renamed, fragmenting historical lineage;
- punctuation and normalization become identity rules;
- a name is a poor cross-system join key; and
- revisions become ambiguous.

A unique human name can still be an excellent display value. The recommended model is:

    canonical identity:
      dataregistry://<cluster>/<project> / <asset UUID>

    display:
      Customer documents

    physical alias:
      s3://sample-data / raw/documents.csv

The current DatasetEvent already carries a human-readable description through
DocumentationDatasetFacet, plus ownership and the symlink. A future governed registry
facet could carry assetId, displayName, registry URL, classification, and assurance.

Duplicating assetId in a facet is harmless but not necessary because it is already the
dataset name.

The best user experience is for the RHOAI Data Registry or lineage UI to resolve the
UUID through the registry API and display Customer documents while retaining the UUID
for identity, URLs, joins, and API calls. Do not make Marquez's raw UUID label the only
customer-facing view.

### What about revisions?

Do not mutate the existing dataset name to a new display name or version in place. If
immutable revisions are introduced, keep the stable asset anchor and create explicit
revision identities, for example:

    dataregistry://<cluster>/<project> / <asset-id>@v3

Then pass that revision identity consistently through ingestion and downstream events.
A revision counter alone does not prove that bytes changed; the sample's current
assurance is Linked, not Observed or Reproducible.

## 9. What Marquez can and cannot answer visually

| Question | Marquez graph | API/facets/registry needed |
| --- | --- | --- |
| Where did this artifact come from? | Often yes, by following upstream edges. | Registry join for friendly name and owner. |
| Where is this asset used? | Direct downstream exploration. | Alias resolution and transitive impact closure. |
| What could be affected? | Partial graph traversal. | Registry-aware impact report and owner joins. |
| Why is an artifact wrong? | Run/job navigation. | Parameters, schema, statistics, errors, logs, and run comparison. |
| Who owns the input? | Maybe an ownership facet. | Registry API is authoritative. |
| How do components interact? | Job and dataset graph. | Parent/root correlation and job grouping. |
| Were source bytes unchanged? | No. | Hash, ETag, version, or manifest evidence. |
| Is output reproducible? | No, not from Linked lineage alone. | Immutable source and execution evidence. |

This is the product conclusion: Marquez is a valuable backend and exploratory UI, but
RHOAI should expose task-oriented views on top of it:

- Provenance: start at an output and show upstream registry asset, owner, and path.
- Impact: start at a registry asset and show downstream jobs, assets, and owners.
- Run diagnosis: show parameters, schemas, statistics, failures, retries, and logs.
- Component map: collapse technical Spark nodes into the business processing stage.
- Assurance: label edges Linked, Observed, or Reproducible.
- Identity resolution: show display names while retaining canonical namespace/name pairs.

Generating OpenLineage JSON is only the instrumentation step. Customer value comes from
indexing, joining, resolving, traversing, and presenting the data in these workflows.
